# 坑 01：Windows 中文路径 base64 传输

## 症状

FastAPI/uvicorn 服务（如 docling-server）收到中文路径的转换请求时，返回 `500 Internal Server Error`；服务端日志里路径变成乱码：

```
ConversionError: ... No such file or directory: 'D:\\...\\����_���ְ�.pdf'
```

拉丁路径（`test_scan_1p.pdf`）正常，中文路径（`报告_文字版.pdf`）必挂。

## 根因

- curl `--data-urlencode` 把 UTF-8 中文做**百分号编码**（`%E6%8A%A5...`）
- FastAPI/starlette 在 **Windows** 上按 **GBK/cp936** 解码这个百分号串
- UTF-8 字节流被 GBK 解读 → 乱码 → 文件不存在 → 500

Linux/macOS（locale 通常 UTF-8）不触发，所以这是 **Windows + starlette 的隐藏坑**。

## 解法：base64 传输（纯 ASCII）

```bash
# 客户端（shim 内）
B64=$(printf '%s' "$WIN" | base64 -w0)   # 中文 → 纯 ASCII
curl -s -X POST "http://127.0.0.1:5001/convert" \
  --data-urlencode "path_b64=$B64" --data-urlencode "light=1"

# 服务端
import base64
path = base64.b64decode(path_b64).decode("utf-8")  # 还原
```

base64 输出只有 `[A-Za-z0-9+/=]`，任何 locale 下都按 ASCII 处理，**彻底绕开编码链路**，不存在歧义。

## 要点

1. 不要试图"修" starlette 的编码——那是 locale 问题，改不动也改不稳
2. 传参名用 `path_b64` 而非 `path`，让调用方一眼知道传的是编码后值
3. 中文路径是常态（用户文件名很少是纯 ASCII），这条必须处理

# 坑 03：分层路由与降级链（本仓库灵魂）

## 问题

常见做法是"一个引擎处理所有文档"（如全用 pymupdf、或全用 docling）。结果：

- PDF 扫描件丢给文字提取器 → 输出空
- 纯文字 PDF 丢给 OCR → 慢且没必要
- 引擎出 bug/格式不支持 → **整批失败**

## 解法：分类驱动 + 链式降级

```
Office(docx/pptx/xlsx) → anydoc（Rust，毫秒级，LLM-ready）
PDF                      → 先分类（pdf-inspector type，10-50ms）
                            ├─ text_based  → pdf-inspector md（位置感知：多栏/表格/标题）
                            │                 └─ 空输出（无 ToUnicode 中文字体）→ 降级 docling --scan
                            ├─ scanned/image_based → docling --scan（GPU OCR，rapidocr 中文）
                            ├─ mixed       → docling 全能力（含文字页表格/公式，不弱化）
                            └─ 分类器失败  → pymupdf 阈值兜底（字符<60 或非空页<0.2 → scanned）
```

## 设计原则（别人学这套时照抄的）

1. **每类文档用最优引擎**——不是最准的，是最"匹配任务"的
2. **降级是链不是跳板**——一个环节失败不是结束，落到下一档继续
3. **分类器本身也要兜底**——分类是路由入口，它挂 = 全挂，所以 pymupdf 阈值是最后防线
4. **失败显式化**——进 `_failed.txt` + stderr + 非零退出码，绝不静默吞
5. **输出也要回环**——`<50 字符` 记 `[warn] 输出过短`，防止"转出来了但转错了"静默通过

## 实测数据

- 批量混合（文字版 + 扫描件）：**4 秒**（GPU serve 下）
- 分类耗时 10-50ms，几乎可忽略
- 兜底路径：pdf-inspector 挂 → pymupdf 判定 → docling OCR，全程无人工
